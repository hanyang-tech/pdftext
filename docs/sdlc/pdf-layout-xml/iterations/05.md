## Requirements and design
Iteration 4's lane a reviewer (`iterations/04a/reviewer-r1.md` #1 and its design issue) found that pdfminer's ASCII85 marker regexes, `^\s*<?\s*~\s*` and `\s*~\s*>?\s*$`, are quadratic on whitespace and run as one C call holding the GIL. A 1 MB whitespace ASCII85 content stream hung the CLI for more than 3 min 41 s at the defaults, because the watchdog thread can't run, so neither the page timeout (SEC-2) nor the hard stop (SEC-3, threat row 3) fires. The driver confirmed the cost: 20 KB took 0.7 s, 40 KB 2.7 s, and 80 KB 10 s. The problem is older than iteration 4, since pdfminer's own `ascii85decode` makes the same calls, but it breaks AC-25's "never a hang". The design says to size ASCII85 "after pdfminer's own stripping", and threat row 3 assumes the hard stop covers C code. Both are design contracts, so this goes to the architect as a delta (backlog #63, `must`), then to the user's gate.

Architect (general-purpose, opus), 17:12Z–17:43Z, report `05/architect-delta.md` (contract check passed, 0 send-backs; all ten `design.md` sections present, SECURITY CRITERIA and `DESIGN: READY`). The driver re-ran two of its probes: the linear strip matched pdfminer's regexes on all 299,593 inputs up to length 6 and 200,000 random ones, and 40,000 spaces took 2.4 s through the regexes against 0.0001 s linear.

Proposal:
- **Q1, the strip.** Under a limit, the bounded `ascii85decode` replaces pdfminer's two marker regexes with `_strip_ascii85_markers`, a linear equivalent proven exhaustively and by fuzzing the whole decode. The no-limit path stays pdfminer's original (SEC-19). A test pins the two regex patterns. 32 MiB of whitespace strips in 0.058 s; the reviewer's `ws85.pdf` converts in 0.09 s.
- **Q2, threat row 3.** A `Watchdog` with `hard_stop=True` on the main thread (the CLI) also arms a SIGALRM interval timer (repeat 0.5 s) whose handler raises the due stop. `_sre` and big-int arithmetic check signals, so a GIL-holding regex is stopped at its deadline with the normal page error (2.08 s against 2 s, exit 3). The polling thread and its hard stop stay for C calls that release the GIL. Rejected: faulthandler (exit 1 and a traceback), SIGALRM's default action (no line), a handler calling `_hard_exit` (raced), a process per page (INV-3), a native watchdog (compiled dependency).
- **Q3, survey.** No other super-linear single C call on pdftext's path at the defaults. The named remaining gap (Risk 14): a GIL-holding call that doesn't check signals (sorts, bytes methods; under about 2 s at the defaults), and any GIL-holding call in the library without `hard_stop` or off the main thread.
- **Criteria.** SEC-3 split into (a) a signal-checking GIL-holding call gives the page error and (b) a GIL-free call that ignores signals gets the hard stop; SEC-20 added for the linear strip. AC-25 and SEC-2 unchanged.
- **Side effect.** Tests that model "stuck in C" with `time.sleep` must block SIGALRM, since the alarm now interrupts the sleep. `hard_stop=True` owns SIGALRM for the run and restores the previous handler.
