## Requirements and design
Release (`release/security.md` #1, reproduced by the driver) found that `max_stream_bytes` bounds FlateDecode only: pdfminer decodes RunLengthDecode and LZWDecode outside the zlib shim, so SEC-1 holds only for Flate. Threat row 1 names zlib as the only route, so the fix needs a mitigation the design doesn't have. It goes to the architect as a delta (backlog #44, `must`), together with the default's sizing (backlog #45, `release/security.md` #2 and the second design issue), since both set the same bound.

Architect (general-purpose, opus), 06:53Z–07:31Z, report `04/architect-delta.md` (contract check passed, 0 send-backs; all ten `design.md` sections present). `DESIGN: READY`. It found the gap wider than the finding: every non-Flate filter, both predictors and Flate's own corrupt-data retry escape the limit, and CCITTFax costs 13 to 67 times its output. Proposal: nine bounded decode filters replacing the one zlib shim; `max_stream_bytes` from 256 to 32 MiB; CCITTFax refused under a limit; content-parser amplification accepted as threat row 4's fatal stop; SEC-1 and SEC-19 reworded to name the routes. Design gate: the user accepted all four recommended answers (32 MiB default; CCITTFax refused under a limit; parser amplification accepted, backlog #60; SEC-1 and SEC-19 reworded as proposed). Applied to `requirements.md`; the driver changed `design.md` C3 to "bounded decode filters". `README.md`'s `--max-stream-bytes` row (256 → 32 MiB) is edited at Integrate.

## Retro
- **Delivered:** lane a SEC-1 (every decode route), SEC-19 (re-checked across the filters), AC-25's 32 MiB default and exact-limit cases; lane b `convert.sh` exit ranking, help, safe names and shared folders, the README limits wording, and a deterministic AC-23 memory test. Release security finding #1 and #2 are closed.
- **Learned:**
  - A bound on output size isn't a bound on time. Every filter is now sized before it allocates, but the step that strips ASCII85's markers is two regular expressions that are quadratic on whitespace, and a C call holding the GIL stops the watchdog thread too, so neither the page timeout nor the hard stop (threat row 3) can end it. The design assumed the hard stop covered "stuck in C code"; it only covers C code that releases the GIL or returns to Python. That assumption reaches past ASCII85: any long GIL-holding call in pdfminer, pdfplumber or the standard library (another backtracking regex, a huge `bytes.translate`) has the same gap.
  - Sizing the architect's prototype exactly paid off: the engineer's exact ASCII85 and ASCIIHex bounds avoided refusing streams that decode to exactly the limit.
  - Two lanes with no shared file merged cleanly again; planning lane b before the gate kept it off the critical path.
- **Time:** 10 h 17 min wall-clock, nearly all of it waiting on the design gate. Lane a's build and verify took 27 min in one round, the fastest full-verify lane so far. No flaky tests: lane b's deterministic memory test passed 37 of 37 runs and the full suite once.
- **Queued:** #63 (`must`, design): the ASCII85 hang and threat row 3's GIL assumption, for an architect delta and the user's gate. #64 (seam originals from `pdftypes`) can join #51's self-check. #54 to #62 minor or optional. PAT-5 still waits for the user's confirmation at Release.
- **Next:** iteration 5 starts at Design: the architect decides how the ASCII85 strip becomes linear (fuzzed against pdfminer's regexes for INV-1), and whether the hard stop moves off the GIL or threat row 3 names the gap. Then the user's gate, one lane, Integrate, and Release again.
