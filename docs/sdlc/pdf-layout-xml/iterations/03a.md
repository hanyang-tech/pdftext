## Plan
- **Slice:** a hostile PDF can't hang or exhaust the host: every configured limit stops it with exit 2 or a page-level error; PDFium repair is safe across threads and stops; "encrypted" follows the trailer. Backlog #7 (limits code only; its test-only criteria are lane c), #20, #21 and #9. Concretely, from `design.md` (Limits, Adapter, Library and CLI contracts; Decisions; Risks 6, 9, 12, 13; threat rows 1 to 6, 15, 20, 21):
  - `limits.py` enforcement: the size check before the parser opens the file (and bounding `_repair_and_start`'s whole-file read), `/Count` over `max_pages` refused before any page is read, `max_pages` counting failed entries and stopping a falsely small `/Count` at the limit, the per-page character limit, the memory limit, and the page timeout;
  - the watchdog: `StructureTimeout` armed over `open_document` and each `advance`, the walker's `except` widened to `(Exception, StructureTimeout)`, `read` raising a stored `StructureTimeout` as `PageTimeout`, the stop re-delivered until `disarm`, `_Entry.outcome`'s type and both `isinstance` checks widened; the CLI's grace-period exit when the main thread is blocked in a C call (SEC-3);

  - README: the library's thread-safety promise (`iter_pages` and `convert` may run on several threads, one generator per thread);
  - decide whether `--page-timeout inf` is allowed (accepted today; `01a/reviewer-r1.md` U18) and say which in the report;
  - close #9 when SEC-16's `/Count` cycle clause passes.
