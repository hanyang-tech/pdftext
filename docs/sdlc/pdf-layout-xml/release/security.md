FINDINGS:
[#1] MAJOR · src/pdftext/adapter.py:79-83 · security: `max_stream_bytes` bounds only FlateDecode. pdfminer's `PDFStream.decode` (pdfminer/pdftypes.py:309 onward) sends RunLengthDecode to `rldecode` and LZWDecode to `lzwdecode`. Neither goes through the shim, so SEC-1, row 1, row 21, and README line 66 ("that page is an error page, exit 3") hold only for Flate. · Measured with `uv run pdftext`:
- A 64 MiB file whose page 2 content stream is RunLength-encoded and inflates to exactly 4 GiB, at default limits: `pdftext: error: memory limit exceeded`, exit 2, 2.37 GB peak RSS, after 0.94 s. Only `page-0001.xml` was written and there is no `document.xml`. SEC-1 requires an error page for page 2, exit 3 and peak RSS under 1 GiB.
- A 4 MB RunLength file with `--max-stream-bytes 1048576`: the same fatal stop, 2.35 GB, in 1.35 s. `rldecode` builds a `list[int]` (about 8 bytes per output byte), so memory grows about 512 times the file size.
- An 83 KB LZW file decoding to about 199 MB, with `--max-stream-bytes 1048576`: the same fatal stop, 2.21 GB, in 21.9 s. In process, `lzwdecode` under a 1 MiB shim limit returned all 199,320,880 bytes.
- In a host running several conversions on threads, the process-wide memory poll then stops every run, not just the hostile one.

Fix: bound every decode filter, not just zlib. Replace `pdftypes.rldecode` and `pdftypes.lzwdecode` with versions that stop at `_stream_limit.max_bytes` and raise `LimitExceededError`, or wrap `PDFStream.decode` and check the output size after each filter. Cover CCITTFaxDecode, ASCII85 and ASCIIHex too. Add RunLength and LZW cases to `tests/test_limits_run.py` (SEC-1) and `tests/test_stream_limit.py` (SEC-19).

DESIGN ISSUES:
- Threat row 1 and AC-25 treat FlateDecode as the only route to a stream bomb ("Bounded zlib, `max_stream_bytes`"). SEC-1 is stated for any content stream that inflates to 4 GiB, and pdfminer decodes RunLength, LZW and other filters with no bound. As designed, the mitigation can't satisfy SEC-1 (finding #1).
- The AC-25 defaults rationale argues that per-page hazards end in a page error before the 2 GiB memory limit, because the char limit (about 480 MiB) fires first. It doesn't account for content-parser amplification of a stream under `max_stream_bytes`: about 10 times, so a 256 MiB stream needs about 2.5 GiB. A stream under the default limit therefore reaches SEC-4's fatal stop instead of an error page (finding #2). The `max_stream_bytes` default needs its own sizing against `max_memory_bytes`, and row 4 ("other routes") should say whether that outcome is intended.
